# Recompiler generator and guest runtime: current state

Owner: P1 generator track. Describes what exists now; Git history is the changelog. Target: NTSC-U `GYWEE9`, `main.dol` SHA1 `1ccfd9dfb5c250c2f45c70c74cc45e5d88d22374`. Background and feasibility numbers: `recomp-feasibility.md`. The contract with the platform track is `tools/recomp/runtime/hle_abi.h` (architect-owned).

## Milestone 1: shared contract (done)

### Machine and thread state

`rt::Machine` (`tools/recomp/runtime/guest.h`) is the shared guest machine: guest memory (`mem`, `lc`), the recompiled function table (`functions`, `functionCount`, defaulting to the generated `kFunctions`), the retired-instruction counter `icount`, the instruction `limit`, and the census/trace diagnostics. `rt::Ctx` is the CPU state of one guest thread: GPRs, FPRs, CR, XER, LR, CTR, FPSCR, GQRs, storage SPRs, MSR/SR, reservation, `pc` and the shadow call stack. A `Ctx` is built from a `Machine` (`Ctx(Machine&)`, no default constructor) and reaches it through `c.m`. `createThreadContext(parent)` makes a zero-initialised `Ctx` on the parent's machine; it copies no registers, and each context has its own shadow stack (8192 frames, about 100 KB per context).

The retired-instruction counter is shared by all threads, so the default time base stays deterministic across contexts. Generated code ticks it with `rt::tick(c, n)`.

### Contract implementation (`guest.cpp`)

| Function | Behaviour |
|---|---|
| `hleRegister` | Stores `(addr -> name, handler)` in a process-wide table. A duplicate address or a null handler throws `Stop{Contract}` carrying the address and the registered name. The name must have static storage. |
| `hleCall` | Looks up the handler, retires one instruction (sets `pc` to the replaced function, so the instruction limit applies), runs it, and restores LR to its entry value (the replaced function's `blr` leaves LR unchanged). An unregistered address throws `Stop{HleUnregistered}` with the address and, when the generated name table knows it, the SDK name. |
| `mmioInstall` | Installs both models, or neither (uninstall). Passing only one throws `Stop{Contract}`. |
| Loads/stores | Plain memory (MEM1 at `0x80000000`/`0xC0000000`, locked cache at `0xE0000000`) is inline; everything else goes to `loadSlow`/`storeSlow`. In `0xCC000000-0xCC00FFFF` (access wholly inside) they call the installed model with the width (1, 2, 4, 8) and the value in guest numeric order; reads are masked to the width. Outside the window, or with no model installed, the access stops with `StopKind::Mmio` (`0xCC000000-0xCDFFFFFF`) or `Fault`. `dcbz` on hardware addresses stops instead of being routed. Census mode (`--census`) still absorbs unmodelled accesses when no model is installed. |
| `timeBaseInstall` | `mftb`, `mfspr` TBL (268) and TBU (269) call the source with the executing `Ctx`. Without one: retired instructions / 4. |
| `createThreadContext` / `destroyThreadContext` | `new Ctx(*parent.m)` / `delete`. No fibers are touched. |
| `callGuest` | Looks up a recompiled entry (anything else stops with `BadIndirect` and the address), pushes a shadow frame whose site is the current `pc`, runs it, pops it, and restores LR and `pc`. A callee's `blr` is therefore validated like any other call, including thread entries on a fresh context. |
| `declareHleNames` | Runtime-internal (`guest.h`, not in the ABI): the generated dispatch table passes `{addr, name}` pairs from the manifest so `hleCall` can name an unregistered function. |

### Manifest and generation

`awl-recomp gen` reads `tools/recomp/hle_manifest.txt` (override with `--hle-manifest FILE`; it is an error if the file cannot be opened). `tools/recomp/manifest.{h,cpp}` parses the documented line format and rejects, with `file:line:` diagnostics (all problems are reported): a module other than `dol`, missing or extra fields, an address that is not `0x` plus 1-8 hex digits, an unaligned address, a name that is not an identifier, missing `#` evidence, and duplicate addresses. Comments, blank lines and CRLF are accepted, and an empty manifest is valid. After discovery every address must be a discovered function start, otherwise `gen` fails. For each entry the generator emits `void f_XXXXXXXX(Ctx& c) { rt::hleCall(c, 0xXXXXXXXX); }` instead of the recompiled body (a manifest entry also takes precedence over a platform-evidence stub), treats the function as a leaf when computing the boot closure, and adds the name table. Output is ordered by address, so repeated runs give identical files.

### Evidence

- Tests: `recomp_contract_tests` (64 checks: MMIO routing and byte order at widths 1/2/4/8 and for float forms, window edges, no-model stops, duplicate/null/unregistered HLE, handler argument and result passing in r3, f1 and r3:r4, `callGuest` nesting and LR/pc restoration, two contexts with independent registers and shadow stacks, time base source) and `recomp_manifest_tests` (115 checks: parser accept/reject cases, validation against a hand-built program, emission in whole-DOL and boot-path modes, determinism). Expectations are derived from the contract text, big-endian numeric order and IEEE-754 encodings, not from implementation output.
- The boot-path runner (`awl-recomp-spike`, 1,736 functions) gives byte-identical output before and after the split: same stop at `0x801B3AC0` after 133,730 instructions with the same call trace, the same `--trace 4` output, and the same census output. Debug and Release agree.
- End-to-end smoke (local only): a manifest entry on `0x801B3AC0` makes the runner stop with `HLE FUNCTION WITHOUT HANDLER`, naming `OSTestPiSetup`.

### Open points and risks

- Storage-only SPRs (HID0/1/2, WPAR, DMA registers, BATs, SRR0/1, SPRGs) live in each `Ctx` as the contract lists them, so a thread does not see another thread's writes. Real hardware has one set. If the game reads back such a register on another thread, they should move to `Machine`; tell the generator track if the platform track hits this.
- The host floating-point environment (`MXCSR`, set by `syncHostFp`) is per OS thread, not per `Ctx`. The platform track's fiber switch should call `syncHostFp(c.fpscr)` for the context it resumes.
- `hleCall` does a hash lookup per call. If it shows up in profiles, the generator can emit a cached slot per function.
- Memory accesses now reach `mem` through `c.m->mem` (one extra load per access). Not measured; revisit with the first performance run.

### Portability (clang-cl)

Not compiled with clang-cl (not installed). Constructs that may need attention: `<intrin.h>` with `_byteswap_ushort/ulong/uint64` and `_BitScanReverse` (clang-cl provides them, GCC-style compilers do not); `<xmmintrin.h>` `_mm_setcsr` (portable to clang and GCC on x86); reliance on `/fp:strict` semantics (clang-cl maps it to `-ffp-model=strict`; the generated `std::fma` calls must not be contracted or reassociated); `[[noreturn]]` functions that throw (standard); `goto` into labels after declarations (the generated functions declare `ea` before any label; keep it that way). Generated code uses no MSVC-only extension.

## Contract extension: preemption, host data, locked-cache DMA (done)

- **Preemption.** `Machine::checkAt = min(instruction limit, deadline - 1)` is the single value `rt::at` compares the retired count against, so the limit and the deadline share one fast compare. The limit is changed with `Machine::setLimit`, the deadline with `preemptDeadlineSet`, and both refresh every live machine (`preemptInstall`, `preemptDeadlineSet` and the limit are process-wide). The generator emits a checkpoint (`rt::at(c, pc, 0)`) at every return (including conditional `blr`), backward `b`/`bc`, jump-table dispatch, indirect tail call, tail branch and fall-through into the next function; calls already pass through `rt::at`. When the count reaches the deadline the hook runs on the current context. It does not nest on a context already inside the hook (guest code the hook runs with `callGuest` passes checkpoints silently), but another context that reaches a still-due deadline enters the hook itself. A hook that returns with the deadline at or below the count stops with `StopKind::Contract`. The instruction limit is checked first and still stops with `InstructionLimit`. With no hook installed no deadline applies. The hook must save and restore any registers it disturbs: an interrupt delivered at a checkpoint interrupts arbitrary guest code.
- **Host data and contexts.** `setThreadHostData`/`threadHostData` store one pointer per `Ctx`. A new context has every register zero, an empty shadow stack and null host data. `callGuest` leaves the callee's r3/r4/f1 in the context and restores pc and LR.
- **Locked-cache DMA.** `mtspr` 923 (DMA_L) performs the transfer described by DMA_U (922) and DMA_L per the Gekko User's Manual layout (see `lockedCacheDma` in `guest.cpp`): length in 32-byte blocks (0 = 128), DMA_LD set loads memory into the cache, clear stores it. It completes instantly and DMA_T/DMA_F read back clear. A memory range outside MEM1 or a cache range outside the 16 KB at `0xE0000000` stops with `Fault`, naming the address and the `mtspr` pc. Evidence: `recomp_semantics_tests` (13 checks) with expectations from the manual's field layout and the SDK's flag values `0x12`/`0x02`; the loader of the field layout is the manual, not the implementation.
- **Evidence.** `recomp_contract_tests` now has 86 checks (a register-only loop is preempted at its backward branch with count in `[deadline, deadline + 2]`; limit and deadline interplay; no-progress hook; same-context and cross-context hooks) and `recomp_manifest_tests` checks the emitted checkpoints. With an empty manifest the boot-path runner output, trace and census are byte-identical to before (checkpoints retire no instructions).

## M2 (in progress): MMIO-only functions and incremental output

- **Platform evidence no longer stubs MMIO-only functions.** A function is emitted as a `platformBoundary` stub only when it has privileged evidence (`rfi`/`sc`), is not the DOL entry and has no manifest entry. A function whose only evidence is constant-address MMIO is recompiled, its accesses reach the installed `mmioInstall` models, and the boot-closure walk continues into it. The evidence stays visible in the generated source (`// platform evidence: MMIO PI x1` above the function), in `awl-recomp discover` and in `--census` (unmodelled accesses are still recorded as absorbed faults). `awl-recomp gen` prints the number of MMIO-only functions it recompiled.
- **Stable chunks.** Generated functions are grouped by 32 KB address window of their start address into `gen_<window>.cpp` (for example `gen_80008000.cpp`); a function only ever lands in the chunk of its own address window, and no file name or content depends on the rest of the output. `gen_decls.h` and `sources.cmake` change only when the function or file set changes, and `gen_dispatch.cpp` when the function set or the manifest names change. Every file is written only if its content differs from the file on disk, so untouched files keep their timestamps and MSBuild skips them. Chunk files from earlier runs that are no longer part of the output (`gen_*.cpp`) are deleted.
- **End-to-end test.** `recomp_generated_tests` compiles generator output for a hand-assembled DOL (`tests/recomp_synth_dol.cpp`, built and generated by CMake at build time) and checks, on real generated code: an MMIO-only function is recompiled and its store reaches an installed model (while the same access stops with `Mmio` without one), an `rfi` function is still a `Platform` stub, a manifest function stops by name until a handler is registered, and a register-only `bdnz` loop is preempted at its backward branch.
- **Measured (Release, this machine, whole DOL with `--full`, 73 chunk files, 590,929 instructions, 34 MB of C++):** generation takes 2-4 s. The first build of `awl-recomp-spike` against it takes 8 min 5 s (with `/MP` on the target; the compile is dominated by a few large chunks, so `/MP` helped little here). Regenerating with no change writes 0 of 75 files and the build then takes 2.3 s. Adding one HLE manifest entry for one function rewrites 2 files (its address-window chunk and `gen_dispatch.cpp`, which carries the name table) and the rebuild takes 16 s including the link. Before this change every regeneration rewrote every file and the build was the full 8 minutes.
- With the platform manifest the boot path now recompiles 124 MMIO-only functions and has 0 platform stubs (the previous 56 stubs were MMIO-only); the first hardware access the runner reaches is a `PI` register store inside the recompiled `0x801B3AC0` (`0xCC003004` at 133,820 instructions), which stops with `Mmio` until a model is installed. In the whole DOL 31 privileged functions remain boundary stubs and 211 MMIO-only functions are recompiled.

## M3: REL modules (done; awl-host acceptance below)

- **Generation.** `awl-recomp gen --full --rel-dir DIR` also generates every `wlp0/1/2.rel` that exists in `DIR` (`tools/recomp/modules.{h,cpp}`). Each module is linked at a synthetic base (`0x80400000 + (id - 1) * 0x400000`) only for analysis: decoding, function discovery (header prolog/epilog/unresolved entries, `bl`, data pointers, constants) and jump-table resolution run on that image. The synthetic base never appears in generated code. Every address the code uses is the section base the runtime learned at link time plus a fixed offset: function symbols are `m<id>_s<section>_<offset>`, `rt::at`/`AWL_CALL`/`rt::ret` take `rb + offset` (`rb` = `c.m->relBase[id][section]`, loaded once at function entry), so `c.pc`, LR and the shadow-stack frames hold the real linked addresses. Relocations against the DOL are absolute and are patched into the analysed image (REL24 into the DOL becomes a direct call, ADDR16 halves become literals). Relocations against a module (ADDR16_HA/LO/HI/ADDR16 on an `addi`, `addis`, `ori`, `oris`, load or store) are emitted as `c.m->relBase[module][section] + addend` pieces; any other relocated instruction, or an unsupported relocation type, fails generation with a message. Jump tables dispatch on `c.ctr - rb` with section offsets as case labels. ADDR32 data relocations are left to the recompiled `OSLink`, which patches guest memory.
- **OSLink / OSUnlink from evidence.** `findOsLink` finds the SDK strings `OSLink: unknown relocation type` and `OSUnlink: unknown relocation type` in the DOL data, the single function that forms each string address (the relocation routines), the single caller of the first (the `Link` routine), and the single caller of that (OSLink); OSUnlink is the single caller of the second routine. On the local DOL this yields OSLink `0x801B4860` (called from `0x80177BDC`, `0x80177C68`, `0x80177CF4`) and OSUnlink `0x801B4ABC` (called from `0x80177858`), matching the platform track's names. The generator wraps both: the recompiled body is emitted as `f_X_impl` and `f_X` calls `rt::moduleLinked` / `rt::moduleUnlinked` with the `OSModuleInfo` pointer from r3 when the body returns non-zero (both SDK functions return TRUE on success).
- **Runtime.** `moduleLinked` reads `OSModuleInfo` from guest memory (id at +0, section count at +0x0C, absolute section-table address at +0x10; entries `{address | exec bit, length}`), checks the section count and every length against the generated module, stores the section bases in `Machine::relBase`, and registers every module function at `base + offset` in `Machine::dynFunctions` (sorted; `lookupFunction`, and therefore `callIndirect`, `tailIndirect` and `callGuest`, search the DOL table first and then this one). Unknown module id, a count/length mismatch, a double link, an address collision and an unlink of a module that was not linked all stop with `StopKind::Contract` and the values involved. `moduleUnlinked` removes the functions and zeroes the bases. The prolog, epilog and unresolved entries are ordinary module functions and are reachable through `callIndirect` after the link.
- **Evidence.** `recomp_generated_tests` links a hand-assembled REL (`tests/recomp_synth_dol.cpp`; built, generated and compiled by CMake) through generated OSLink/OSUnlink wrappers of a synthetic DOL that carries the SDK evidence strings, and checks: calls through `callIndirect` before and after link, dynamic `lis/addi` addresses at two different load addresses, an internal `bl` and a REL24 call into the DOL with real addresses in the trace frames, a function pointer in relocated data, a four-entry function table, a jump table of linked addresses, unlink followed by relink elsewhere, and each stop. The real DOL and RELs generate 15,635 functions (DOL 12,366 + modules 3,269) with the same 18 untranslated instructions as the DOL alone (none in the modules).
- **awl-host acceptance (local, `main` platform runtime plus this generator output; `awl-host` linked against `awl_recomp_gen`).** The run no longer stops at the first REL prolog (`0x803A2A8C`): the recompiled OSLink succeeds, the generated wrapper registers the module, and the game runs the REL code. With the module tables linked in, the run reaches 134,680,679 retired instructions (about 0.3 s) with 47 retraces, 56 framebuffer latches and 30 EFB copies, then stops with `NON-LOCAL RETURN` at `0x801B739C` on guest thread 3: the final `blr` of the function at `0x801B72BC` (it disables interrupts, unlinks a thread from the run queue, marks it dead with state 8 and calls the scheduler; the SDK's `OSExitThread`) runs with LR different from the shadow-stack return address, right after `switch thread 2 -> 3`. A function that never returns in the original (a dead thread is never resumed) is being resumed, so this is a thread start/exit or reschedule question for the platform runtime, not REL code. The 120-retrace main-loop criterion is therefore not yet met.
- **Linking the generated code.** The generated object `gen_dispatch.cpp` calls `declareGeneratedRelModules()` from a static initialiser so the module tables stay linked when the generated code is a static library (an object that nothing references is dropped by the linker; the first run stopped with "module id 2 has no generated code" for that reason).

|---|---|---|
| Functions emitted (DOL + modules) | 15,635 (12,366 + 3,269) | 15,349 (DOL 12,114 + modules 3,235; 261 DOL and 34 module "functions" are not functions, see below) |
| Functions sharing words with another | 327 (17,547 words) in the DOL, 66 (669 words) in the modules | 0 |
| Unresolved `bctr` in generated code | 10 | 0 |
| Bodies that fall off into undecodable words | 13 | 0 |
| Untranslated instructions | 18 (13 undecodable, 4 `twi`, 1 `bl`) | 1 (the exception-vector template below) |
| Scan-length jump tables (DOL) | 14 | 0 (247 bounded, 1 indirect tail call) |
| Never-returning functions | not analysed | 37; 7 call sites followed by a stop |

**Overlap resolution (`resolve.{h,cpp}`).** Discovery walks every seed as a function, so a heuristic seed inside code another function already reaches yields a second, overlapping "function". `resolveFunctions` drops, from evidence, the ones that are not functions; a dropped function is neither emitted nor in the dispatch table (its words stay in the functions that own them, a computed jump to its address stops loudly with the address, and no direct reference to it can exist, which is what the rules prove):
- *Data in text* (13 in the DOL): a table in the text segment (the `__init` section table at `0x8000561C` and similar) that code reads as data. Dropped when the body reaches an undecodable word and nothing references the start, or when only a code constant names the start and straight-line code from it reaches an undecodable word (executing it from the entry would trap on that word).
- *Jump-table label* (158): a function start that is only a case label. Dropped when it is seeded only by data words, every data word naming it lies inside a jump table whose targets include it, and the label is inside another function's body.
- *Unreferenced fragment* (90 in the DOL, 34 in the modules): seeded only by the gap heuristic, no `bl`, tail branch, fall-through, relocation or data reference, and it duplicates code other functions reach. 2,685 words were reachable only through dropped functions.
After the rules no function shares words with another, so there are no emitted shared tails; the 26 apparent shared-tail functions of the first pass were an artefact of over-scanned jump tables (the verified bounds below removed them). If a genuine shared tail appears later, each function would emit its own copy of the shared code, which is exact because every function body is the closure of control flow from its entry.

**Verified jump-table bounds.** A table is bounded only when the compared register is proven to be the table index: the offset register is `rlwinm rO,rI,2,0,29` and the `cmplwi` is on `rI` with no rewrite of `rI` in between, with the range exit on that condition field being `bgt`/`bge` to a label or `bgtlr`/`bgelr` and no intervening change of that field; or the loop is a counted loop in which the offset steps by 4 exactly when the compared register steps by 1, both from 0 (checked over the loop region). The 14 scan-length tables were compiler range checks that return (`bgtlr`) instead of branching, and 2 counted loops; all now have verified bounds. Tables for which the proof fails stay scan-length and are reported.

**Remaining untranslated item.** `f_801B145C` begins with `bla 0x60` and is one of the exception-vector code templates that `OSInit` copies to low memory (named only by the `lis/addi` constants at `0x801B1214`/`0x801B1258` used as copy sources). The runtime handles exceptions natively, so the template is never executed from here; it stays a loud named stop (`UNTRANSLATED CODE`).

**Other items.**
- `tw`/`twi` are translated: the trap condition is evaluated from the TO bits (16 signed <, 8 signed >, 4 equal, 2 unsigned <, 1 unsigned >) and a taken trap stops with `StopKind::Privileged` ("trap instruction taken: the program exception is not modelled"); a trap that is not taken is a no-op. The four `twi 31,r0,0` functions at `0x80234C30` now stop only when executed.
- A `bctr` is now classified by address, so functions that reach the same dispatch word all resolve it the same way (that was the cause of the 10 unresolved `bctr`).
- Never-returning functions (no return instruction; tail calls and fall-through only into such functions) are found with a fixpoint over the call graph. A `bl` to one of them (except natively replaced functions) is followed by `rt::returnedFromNoReturn`, which stops with `BadReturn` if the callee ever returns, instead of running whatever follows. The set includes the exception-vector templates (gap- and constant-seeded), the main loop `0x8000AA54`, the context loader `0x801B2E0C` and a few SDK routines.
- Regression digest: `gen` writes `gen_digest.txt` (SHA-256 of every generated file and of the whole output, `sha256.h`) and prints the output digest; `--expect-digest HEX` fails the run on a mismatch. CTest `recomp_synth_digest` pins the digest of the synthetic fixture's output (no game bytes); the digest of the real output is printed by `gen` and kept local. A SHA-256 known-answer test covers the hash itself.
- Incremental builds: chunk files are named by 32 KB address window and written only when their content changes (see the incremental-output section above); the digest lets a change that alters the output be noticed deliberately.
- Diagnostics: `awl-recomp overlaps` (classification before/after), `awl-recomp tables` (scan-length tables with their code), `awl-recomp noreturn`, and `gen` prints the places that became loud stops.
