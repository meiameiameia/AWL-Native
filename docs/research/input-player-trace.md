# Input-to-player trace (in progress)

Target: NTSC-U `GYWE41` `main.dol`, SHA1 `1ccfd9dfb5c250c2f45c70c74cc45e5d88d22374`. Addresses below were checked against that DOL with the repository's read-only Ghidra scripts. Raw decompilation and instruction exports are local, ignored `build/player-input-trace/` files. Function labels describe observed behavior only; they are not claims of completed translation.

## Confirmed PAD pipeline

1. `FUN_8000AD40` calls `FUN_80213DA4` at `0x8000AE1C` during startup. The latter initializes PAD-related state at `0x80341430`, configures sample storage and per-channel state, and calls the lower-level `FUN_801C06D4`. The read-only `hmawl` name for `0x80213DA4` is `HSD_PadInit`; behavior here is based on this project's DOL, not copied code.
2. `FUN_8000AA54` calls `FUN_80213CE4` at the end of each main-loop iteration. `FUN_80213CE4` calls `FUN_80212720`, `FUN_802136C8`, and `FUN_80213B44` in order.
3. `FUN_80212720` calls `FUN_801C0824` to collect four low-level controller records, then queues them in 52-byte slots. `FUN_801C0824` reads channel status and distinguishes disconnected/error cases; its complete platform behavior has not been translated.
4. `FUN_802136C8` consumes a queued record, applies stick processing through `FUN_802129CC` and direction/button processing through `FUN_80213180`, and writes per-channel state beginning at `0x80341464`. `FUN_80213B44` copies/filters that state into the consumer-visible array beginning at `0x80341574` (68 bytes per channel).
5. In the consumer-visible first-channel record, `0x80341574` is current button bits, `0x80341578` previous bits, `0x8034157C` newly pressed bits (`current & (previous ^ current)`), `0x80341580` repeat bits, and `0x80341584` released bits (`previous & (previous ^ current)`). The disassembly/decompilation of `FUN_80213B44` supports these exact operations. The remaining bytes include axes/status but require a separate layout audit before PC mapping.
6. `FUN_80213180` adds `0x01000000`/`0x02000000` when the corresponding processed trigger byte is strictly greater than `DAT_80341446`. The initialization template at `0x802E7734` contains repeat delay 45, interval 8, and trigger threshold 145, but `FUN_8000AD40` immediately overrides these to 15, 2, and 120 after `FUN_80213DA4`. `FUN_802129CC` first subtracts the runtime dead zone of 10 from a raw trigger byte of at least 10, so the synthesized bit starts at raw pressure 131. `FUN_801777C4` later calls `FUN_800126FC` to change repeat timing on a system-task/scene transition (`max(1, 30 / param)` and `max(1, 6 / param)`). `FUN_800126EC` supplies that nonzero divisor from a scene-indexed table at `0x802980D8`; populated entries inspected so far are 1 or 2, yielding 30/6 or 15/3. The native harness has no translated scene transition to select the divisor, so it retains the startup 15/2 until explicitly updated.
7. `FUN_802129CC` applies the same radial processing to main and C sticks: radius below 10 clears both signed axes; radius above 82 scales both axes to 82 and truncates toward zero; nonzero radius then loses 10 along its own direction and truncates again. `FUN_80213180` synthesizes main-stick bits `0x40000` left, `0x20000` down, `0x80000` right, and `0x10000` up only when the processed radius is at least 30. The C-stick bits are those masks shifted left four places. The sector boundaries are −3π/4, −π/4, π/4, and 3π/4, with zero angular margin in the DOL initialization template. These values were checked in the verified DOL using the `r2=0x80351E40` register initialization at `0x8000332C` and the constant pool at `0x8034C3A8..E0`. The native equivalent uses standard floating-point square root and atan2; edge behavior near irrational angular boundaries is not claimed bit-identical to the PowerPC math routine.

## World-map character ownership and dispatch

- `FUN_80013F60` (which references `SceneWorldMap.cpp` in the verified DOL) allocates `0x15CC` bytes, constructs the character object through `FUN_8002FDF8`, and stores it at scene offset `+0x24`. The constructor installs tables beginning at `0x8029FF18` and initializes its state through `FUN_80031D7C`. The scene destructor `FUN_800146BC` destroys that same `+0x24` object. Together these provide high-confidence ownership of the world-map player object, rather than just an address-range guess.
- `FUN_80031D7C` writes the state ID at character offset `+0x1364`, then indexes the runtime callback table at `0x802A3AA8` with a `0x3C`-byte stride and jumps via `FUN_80235D7C`. For example, state `0xE0` indexes `0x802A6F28`; its read-only DOL template entry at `0x802A3670` points first to `FUN_80047D3C`. This establishes state dispatch, **not** the gameplay name or full effects of state `0xE0`.
- `FUN_8003083C`, called from several character-state callbacks, reads signed stick bytes at `0x8034158C`/`0x8034158D`, derives a direction using world/camera-related state, updates character fields `+0x136C` through `+0x137C`, and passes proposed/resulting positions through `FUN_8001DE44`, `FUN_80152724`, and `FUN_80030E18`. The meanings and PC equivalents of these surrounding world-space operations remain to be established before faithful movement can be implemented.
- The front half of `FUN_8003083C` is now isolated as `update_world_map_steering`. It converts the filtered main stick to `(x, 0, -y)`, retains the last direction at neutral, normalizes nonzero input, and selects target speed `0.06`, `0.09`, or `0.18` using squared-magnitude thresholds `1049.76` and `4678.5596`. Current speed approaches the target by `0.03` per update; the returned intensity is current speed divided by `0.18`, clamped to `[0, 1]`. The constants are the `r2` values at `0x8034A168..0x8034A180`, reached from the verified `r2=0x80351E40` initialization. `FUN_801B8B60` confirms the comparison uses squared 3D magnitude and `FUN_801B8B1C` confirms normalization.
- For nonzero input, `FUN_8003083C` passes `(direction.x, direction.z)` to the target's atan2 routine, adds camera yaw from camera offset `+0x1C`, builds a Y-axis matrix through `FUN_801B8048`, and transforms the verified constant vector `(0, 0, 1)` at `0x80251130` through `FUN_801B8760`. The matrix instructions at `0x801B8128..0x801B8150` establish rows `[cos, 0, sin]`, `[0, 1, 0]`, and `[-sin, 0, cos]`; therefore the translated facing is `(sin(angle), 0, cos(angle))`. Neutral input preserves the prior facing rather than recomputing it if camera yaw changes. Standard-library atan2/sin/cos are the native equivalent and are not claimed bit-identical at floating-point edge cases. The helper still stops before scene position, collision, animation, and state guards, and is not yet called by a gameplay scene.
- The pre-collision calculation at `0x80030AEC..0x80030C08` is isolated as `propose_world_map_position`. `FUN_801B8AFC` first scales the normalized input direction by current speed. The function then rotates the scaled X-only component by `camera_yaw + radians(4 * scaled_x)` and the scaled Z-only component by `camera_yaw - radians(4 * scaled_x)`, adds both to the current position, and leaves Y unchanged. The `0.017453292` radians-per-degree and `4.0` factors are the verified DOL constants at `0x8034A184` and `0x8034A188`. This result is only a proposal: `FUN_8001DE44` and `FUN_80152724` subsequently resolve world/collision behavior before the object position is updated. A camera flag at offset `+0x98` can also commit the second component's yaw to camera offset `+0x1C`; that ownership and side effect remain outside the pure helper. Standard-library sine/cosine are not claimed bit-identical at floating-point edge cases.

## Movement collision boundary

- `FUN_80152724` reads the character collision object's runtime category, radius, and flags and forwards the current and proposed positions to the shared resolver `FUN_8001E498`. The collision object at character offset `+0x14CC` is enabled by `FUN_801521D4`; the verified radius constant is `0.3` at `0x8034B630`. Its mode remains zero, so `FUN_801527A8` produces flags `0x67`. Those raw bits select multiple dynamic/static collision passes and radius-aware terrain handling; their complete public semantics are not yet established.
- For runtime category `1`, `FUN_8001E498` maps terrain queries to collision-data slot `10`. `FUN_800209A0` selects `jimen-move.col` or `jimen1-move.col` through the table at `0x80346A08` and loads it into that slot. This establishes that movement collision uses a dedicated COL asset rather than the rendered GPL mesh.
- `FUN_80192258` recognizes the on-disc format byte at offset `4`; type `1` is relocated through `FUN_801925D0`. The type-1 root begins at offset `8`. Each `0x34`-byte node stores quantized minimum XYZ at `+0x00` and maximum XYZ at `+0x06`, followed by four file-relative child offsets at `+0x0C..+0x18`; a zero first child marks a leaf. The coordinate scale is `1 / (1 << header[5])`. `FUN_80192480` descends the X/Z quadtree by comparing the query point with each node's bounds midpoint.
- A leaf stores triangle and vertex counts at `+0x1C/+0x20`, with node-relative payload pointers at `+0x28/+0x2C`. Each 8-byte triangle record is `{surface_flags, vertex_index[3]}` using four big-endian `uint16_t` values. Each 8-byte vertex supplies three big-endian signed 16-bit coordinates; the traced terrain branch reads those first six bytes with an 8-byte stride and multiplies them by the header scale. The final word is zero in every local vertex inspected but has not been assigned broader semantics. The third count/pointer pair at `+0x24/+0x30` is zero in every local COL and remains unsupported rather than guessed. `FUN_801934B4` scans a selected leaf's triangles in serialized order, `FUN_8017C28C` tests X/Z containment with winding-independent edge signs, and `FUN_8017C204` interpolates Y from the first containing triangle.
- The native validator checks the marker, exponent, node bounds, complete child sets, offsets, alignment, cycles, shared nodes, supported payload ranges, and every triangle index. `sample_type1_collision_surface` implements the primary leaf selection, containment, and height interpolation branch. The type-1 virtual at `0x802CB0C0` resolves to `FUN_80193B60`; `FUN_801917FC` calls it at virtual offset `+0x18` after selecting the leaf. `FUN_80193B60` tests all three edges of each triangle in that leaf using `FUN_8017BF00`, keeps the strictly nearest X/Z projection (first edge wins ties), then returns the selected triangle and flags. `FUN_801917FC` applies `FUN_8017C204` to set the projected point's Y coordinate. `project_type1_collision_to_edge` implements this bounded fallback. The type-1 virtual `FUN_80196D88` at offset `+0x1C` belongs to a different collision operation and should not be identified as this fallback. The broader movement resolver remains untranslated. The local `jimen-move.col` is 448,292 bytes and validates as 665 nodes, 499 leaves, 30,437 triangles, 21,276 vertices, and maximum depth 7; `jimen1-move.col` is 452,092 bytes and validates as 673 nodes, 505 leaves, 30,678 triangles, 21,458 vertices, and maximum depth 7.
- In `FUN_8001E498`, category `1` maps to terrain slot `10` at `0x8001EACC`, then calls `FUN_8002009C` at `0x8001EB1C` or `0x8001EB48`. The final argument is derived from the absence of resolver flag `0x800`; the movement object's `0x67` flags enable the terrain height branch. In `FUN_8002009C`, the initial query at `0x8002015C..0x800201AC` uses `FUN_8019163C` for a containing triangle and `FUN_8017C204` for its height. If none contains X/Z, the enabled branch calls `FUN_801917FC` to project to the nearest edge and takes its Y. The radius test at `0x800201B4..0x800201B8` gates additional passes; after any such change, `0x800203EC..0x8002043C` repeats the same height lookup. `0x80020444..0x80020468` writes the candidate X/Z and the sampled Y when enabled. This is high-confidence branch ordering from the verified DOL instruction export; the radius passes and their collision status remain unresolved. `adjust_type1_collision_terrain_height` isolates only that height-enabled query for a validated type-1 asset and reports whether the edge fallback was used. It fails if the selected leaf cannot supply a supported surface, rather than accepting a position without a valid terrain result. It is not connected to player movement.

## Native PAD boundary

`PadAdapter` now maps the first XInput controller and focused keyboard to a raw, first-channel GameCube-style button/stick/trigger sample. The button masks and signed-byte stick/trigger layout follow the [devkitPro libogc PAD header](https://github.com/devkitPro/libogc/blob/master/gc/ogc/pad.h); the target DOL's `0x100` and `0x1000` checks corroborate those two masks in this game. Keyboard defaults are WASD=main stick, arrows=D-pad, Space=A, Backspace=B, X=X, Tab=Y, Z=Z, Q=L, E=R, and Enter=Start. XInput face/D-pad buttons map by name, Back=Z, shoulders=L/R, and the analog triggers generate L/R clicks at pressure 200 or above. Focus loss clears the sample. Press/release edges also retain a complete native tap between sampled frames as a deliberate PC input policy.

The first-channel `HsdPadFilter` now applies the verified radial main/C-stick processing, direction bits, trigger processing, and `FUN_80213B44` current/previous/pressed/released/repeat transitions. It starts with the game's startup repeat timing (15/2) and supports an explicit timing update, but the actual system-task transition is not yet translated. A complete tap entirely between samples is retained by the raw native `PadFrame` but does not appear as a held or pressed HSD button, matching the DOL's sampled-state formula. This is a deliberately partial platform equivalent, **not** a complete copy of `FUN_802136C8`/`FUN_80213B44`: the sample queue, all status/error cases, other normalized fields, rumble, game actions, and player movement are not implemented. The XInput/keyboard layout and click threshold are PC control defaults, not claims about the GameCube game.

## Downstream leads, not yet translated

- `FUN_800472BC` reads pressed bit `0x100` at `0x8034157C` before branching through a large context-dependent interaction/state path. `FUN_800471F8` checks pressed bit `0x1000` after a separate eligibility check, then calls `FUN_800310A4` and `FUN_80031D7C` with state `0xE0`. The gameplay meanings of these masks and state numbers have **not** been established from this trace.
- `FUN_800372D8` reads held bit `0x100` at `0x80341574`. The state callbacks and `FUN_8003083C` are now linked to the world-map character object, but action semantics, movement/collision effects, and state guards are not fully translated.
- The prior hypothesis that `FUN_8012F3E0` initializes input is disproven: its body and `FUN_8012F480` operate a registry of world subsystems. It must not be translated as PAD setup.
